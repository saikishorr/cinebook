## The goal

CineBook moves from one made-up cinema with 2 screens to **the real cinemas of Pune** (Pune and
Pimpri-Chinchwad), each running **all the films now playing in India in every language**: Marathi, Hindi,
English, Telugu, Tamil, Malayalam, Kannada and others. Movies already come from TMDB through
`scripts/import_tmdb.py`. Cinemas will come from **OpenStreetMap**.

**Important constraint, and the reason for the "demo" wording below.** CineBook has no agreement with PVR,
INOX, Cinépolis or any other cinema, and no real showtime feed. Do **not** scrape BookMyShow, District, Paytm
or cinema websites. The cinemas (name, area, address and location) are real public data. **Showtimes, prices
and seat maps are generated by CineBook**, and every ticket is a **demo ticket that is not valid for entry**.
Every customer-facing text you write must make this clear: email, SMS, help content and the chat assistant.

The frontend is being built **at the same time** against the contract in Part C, so implement it exactly.

## Part A: data model (migration `009_cinemas.sql`)

```sql
CREATE TABLE cinemas (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  osm_id      TEXT UNIQUE,                 -- "node/123", "way/456"; NULL for the legacy demo cinema
  name        TEXT NOT NULL,               -- display name, e.g. "PVR Icon Pavilion Mall"
  chain       TEXT NOT NULL,               -- "PVR INOX", "Cinépolis", "E-Square", "City Pride", "Miraj", "Carnival", "Independent", ...
  area        TEXT NOT NULL,               -- Pune locality, e.g. "Shivajinagar", "Kothrud", "Hinjawadi"
  address     TEXT,
  city        TEXT NOT NULL DEFAULT 'Pune',
  latitude    DOUBLE PRECISION NOT NULL,
  longitude   DOUBLE PRECISION NOT NULL,
  is_active   BOOLEAN NOT NULL DEFAULT TRUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
ALTER TABLE screens ADD COLUMN cinema_id BIGINT REFERENCES cinemas(id);
ALTER TABLE screens ADD COLUMN format TEXT NOT NULL DEFAULT '2D'
  CHECK (format IN ('2D', '3D', 'IMAX', '4DX', 'ICE', 'Dolby Atmos'));
-- Screen names are now unique per cinema ("Audi 1" exists in many cinemas).
ALTER TABLE screens DROP CONSTRAINT screens_name_key;
ALTER TABLE screens ADD CONSTRAINT screens_cinema_name_key UNIQUE (cinema_id, name);
CREATE INDEX idx_screens_cinema_id ON screens (cinema_id);
CREATE INDEX idx_cinemas_active ON cinemas (is_active);
```
- **Legacy data.** The migration creates one cinema, `CineBook Demo Cinema` (chain `Independent`, area
  `Pune`, `is_active = FALSE`), and attaches the existing `Screen 1` and `Screen 2` to it. Existing bookings
  must still read correctly.
- After the migration, `screens.cinema_id` is `NOT NULL`.
- Check the real constraint name (`screens_name_key`) in `db/schema.sql` before you drop it.

## Part B: importing cinemas and generating programmes

### B1. `scripts/import_cinemas.py` (with a PowerShell wrapper, `scripts/import-cinemas.ps1`)
- Query the OpenStreetMap **Overpass API** for `nwr["amenity"="cinema"]` inside the Pune + PCMC bounding box
  `(18.40, 73.70, 18.75, 74.05)` with `out center tags;`.
  - Try the mirrors in order: `https://overpass-api.de/api/interpreter`,
    `https://lz4.overpass-api.de/api/interpreter`, `https://overpass.private.coffee/api/interpreter`.
  - Retry with backoff on 429, 502, 504 and connection resets. The main server is often at capacity.
  - The developer's ISP resets some HTTPS connections, so retry generously, as `scripts/import_tmdb.py` does.
  - Send a generic `User-Agent: CineBook-importer`.
- In a dry run, the query currently returns about **39 cinemas**. Examples: "PVR Icon - Pavilion Mall",
  "Cinepolis West End Mall", "E-Square Multiplex" (twice: Ganeshkhind Road and Hinjawadi), "City Pride Kothrud",
  "City Pride Multiplex" (Satara Road), "INOX", "Rahul Cineplex", "Alankar Cinema", "Victory Cinema",
  "Miraj cinemas", "Carnival Cinemas" and "Mangala Multiplex".
- **Area.** Use `addr:suburb`, then `addr:city_district`. Otherwise run a second Overpass query for
  `node["place"~"suburb|neighbourhood|quarter"]` in the same box and take the **nearest** place to the cinema's
  coordinates (haversine distance).
- **Names.** Generic names ("PVR", "Inox", "INOX Leisure", "PVR Cinemas") become `"<Chain> <Area>"`, for
  example `PVR INOX Kharadi`. Fix capitalisation ("Miraj cinemas" → "Miraj Cinemas").
- **Chain.** Normalise from `brand` and `name`: PVR, INOX and INOX Leisure all become `PVR INOX` (the chains
  have merged); Cinepolis and Cinépolis become `Cinépolis`; E-Square / Vishal E-Square / E-Square Xion become
  `E-Square`; City Pride / Abhiruchi City Pride become `City Pride`; Miraj; Carnival. Everything else is
  `Independent`.
- **Duplicates.** Two entries for the same chain within 300 m are one cinema. Keep the one with more tags.
- **Overrides.** Read a hand-editable file, `db/data/pune_cinemas_overrides.json`:
  `{"exclude": ["node/…"], "rename": {"way/…": "…"}, "area": {"node/…": "…"}}`. Create it, initially empty, with a
  comment line in a `"_readme"` key. OSM can list cinemas that have closed, so the developer must be able to hide
  them without code changes.
- Save the cleaned result to **`db/data/pune_cinemas.json`** and commit it as a snapshot. With `--offline`,
  `setup_local.py` and the tests load cinemas from that snapshot with no network access. Fetch it once now and
  commit it.
- Upsert into `cinemas` on `osm_id`. Mark cinemas missing from the new list `is_active = FALSE`; never delete a
  cinema that has shows.
- **Screens.** Use the OSM `screen` tag when present. Otherwise: PVR INOX and Cinépolis get 6, E-Square 5,
  City Pride 4, Miraj and Carnival 4, other names containing "Multiplex" 3, and single-screen theatres 1.
  Name them `Audi 1…n`. Give each multiplex one premium-format screen: `IMAX` at PVR Icon Pavilion Mall,
  `ICE` at one PVR INOX, `4DX` at one Cinépolis, `Dolby Atmos` elsewhere. All other screens are `2D`.
- **Seats** for each new screen use the existing `seats` table:
  - Multiplex audis: 8 to 14 rows of 12 to 20 seats, chosen deterministically from `hash(osm_id, screen number)`
    so re-runs never change a layout. The rear 2 rows are `PREMIUM`.
  - Single screens: 16 to 20 rows of 22 to 28 seats. The rear 4 rows are `PREMIUM`.
  - Never change the seats of a screen that already exists, because bookings reference them.

### B2. Programme generator: `app/programme.py` (pure, unit-tested), called from `scripts/schedule_shows.py`
`schedule_shows(connection, days=8)` creates shows for today (only start times still in the future) and the
next 7 days, for every active screen of every active cinema, using the active movies:
- **Day.** For each screen, start between 09:00 and 10:30, and start nothing after 23:15. Each show is the
  film's runtime + 20 minutes of trailers and cleaning, with start times rounded up to 5 minutes. That gives
  about 4 to 6 shows a day per screen.
- **Which films where** must be deterministic: seed from `(cinema_id, date)`, never use unseeded `random`.
  - **Multiplexes** carry a wide mix, weighted by TMDB order (the movie row's `id` order) and by language
    demand in Pune. Approximate weights: Hindi 30%, English 22%, Marathi 18%, Telugu 10%, Tamil 8%,
    Malayalam 5%, Kannada 3%, others 4%.
  - Every active film must get **at least 2 shows a day somewhere in the city**, so no film card leads to
    "No upcoming shows".
  - **Single-screen theatres** run 1 or 2 films a day, mostly Marathi and Hindi.
  - A screen keeps the same film for its whole day where possible. Real cinemas avoid switching films every
    show.
- **Prices** (stored on each show, as now; seat type decides regular or premium):

  | Chain | Regular | Premium |
  |---|---|---|
  | PVR INOX, Cinépolis | ₹220–320 | ₹380–520 |
  | E-Square, City Pride, Miraj, Carnival | ₹180–260 | ₹280–380 |
  | Independent | ₹120–180 | ₹180–250 |

  Add +15% Friday to Sunday and after 18:00, and +60% on IMAX, ICE and 4DX. Round to ₹10.
- It must be **idempotent**: never change a show that has bookings or live holds. Running it twice creates
  nothing new.
- It must be fast enough for about 40 cinemas × 4 screens × 5 shows × 8 days (~6,500 shows) in a few
  seconds, using batch inserts.
- **Integrate it.** In `scripts/import_tmdb.py`, change **only** the `save()` function: replace running
  `db/add_upcoming_shows.sql` with a call to your scheduler. The scheduler first frees unbooked future shows of
  inactive films, as the script does now. Do not change the film-selection logic: the frontend developer owns it.
- **`setup_local.py`.** After the seed, import cinemas from the snapshot (offline) and run the scheduler. The
  old `db/seed.sql` and `add_upcoming_shows.sql` stay for the legacy screens only and must not schedule shows for
  inactive movies.

## Part C: API contract (additive; the frontend builds against it now)

All times are ISO 8601 with offset in `APP_TIMEZONE`, as the current endpoints return them.
`date` query parameters are `YYYY-MM-DD` in local time.

### C1. `Cinema`
```jsonc
{
  "id": 12,
  "name": "PVR Icon Pavilion Mall",
  "chain": "PVR INOX",
  "area": "Shivajinagar",
  "address": "Senapati Bapat Marg, Pune",        // may be null
  "latitude": 18.5340, "longitude": 73.8296,
  "screens_count": 6,
  "formats": ["2D", "IMAX"]                     // distinct screen formats, sorted
}
```
- `GET /cinemas` → `list[Cinema]` for active cinemas, ordered by name. It takes these optional filters:
  - `area` (exact match, case-insensitive)
  - `chain`
  - `movie_id` (only cinemas with upcoming shows of that film)
  - `date` (combined with `movie_id`: shows on that date)
- `GET /cinemas/areas` → `list[str]`: the distinct areas of active cinemas, sorted.
- `GET /cinemas/{id}` → `Cinema`, or 404 `{"detail": "Cinema {id} not found"}`.
- `GET /cinemas/{id}/shows?date=` → `list[ShowSummary]`, every film at that cinema on that date, ordered by
  start time. `date` defaults to today.

### C2. Additions to `ShowSummary` (and so to `ShowDetails` and every list that returns them)
```jsonc
"cinema_id": 12, "cinema_name": "PVR Icon Pavilion Mall", "cinema_area": "Shivajinagar",
"cinema_chain": "PVR INOX", "screen_format": "IMAX"
```
`ShowDetails` also gets `"cinema_address"` (may be null), `"cinema_latitude"` and `"cinema_longitude"`.

### C3. Movie showtimes by date
- `GET /movies/{id}/shows` takes optional `date=` and `cinema_id=`. **Without `date` it keeps today's
  behaviour** (all upcoming shows); the frontend will always send `date`. Order by cinema name, then start time.
- `GET /movies/{id}/show-dates` → `list[str]` (`["2026-11-20", "2026-11-21", …]`): dates that still have
  upcoming scheduled shows of the film at active cinemas.

### C4. Additions to `Movie` (list and detail)
```jsonc
"cinemas_count": 23,                          // active cinemas with an upcoming show of this film
"next_show_at": "2026-11-20T21:30:00+05:30"    // null if none
```
`GET /movies` takes optional `language=` and `q=` (case-insensitive title search) and `showing=true` (only films
with upcoming shows). Defaults keep current behaviour. Compute the counts in one query, not one per movie.

### C5. Cinema details on bookings, holds and chat links
Add `"cinema_name"`, `"cinema_area"` and `"cinema_address"` to `BookingDetails`, `ChatLinkSummary` and
`HoldResponse` / `HoldStatus`. Add `"screen_format"` to `BookingDetails`.
